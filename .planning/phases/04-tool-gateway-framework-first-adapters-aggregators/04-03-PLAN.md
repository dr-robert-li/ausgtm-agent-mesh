<objective>
Turn `tools/gateway.py` from an echo stub into the real execution engine and — critically
for parallelism — establish the **adapter-dispatch registry** so every Wave-3 adapter is an
additive own-file module instead of an edit to `execute()` (the advisor's load-bearing
catch #1: without this, HubSpot + GWS + aggregators all edit gateway.py and Wave 3 collapses
to serial).

This plan delivers four collaborators:
1. **ToolSpec D-03 fields** — `integration_style`, `input_schema_ref`, `output_schema_ref`
   surfaced by `load_tool_pack` (manifest already declares them; loader drops them today).
2. **CredentialResolver (D-02)** — `tools/credentials.py`: env-backed, Secret-Manager-shaped,
   resolves by `credential_secret_name` ONLY inside `execute()`; returns None when absent so
   the adapter degrades to the stub. The credential NEVER reaches the graph/agent.
3. **Adapter registry** — `tools/adapters/__init__.py`: a `register(key, fn)` / `get_adapter(key)`
   registry with **lazy-import-on-miss** (a registry-miss attempts `importlib.import_module`
   of the matching adapter module, so a module that calls `register()` at import time is
   actually loaded the first time it is looked up — without this, NO runtime path imports the
   adapter modules and the registry is empty at `execute()` time, silently undelivering SC-1
   and SC-3). The **dispatch key** is derived by `adapter_key_for(spec)`: for direct tools the
   key is `spec.provider`; for aggregator tools the key is the aggregator name derived from
   `integration_style` (`composio_aggregator`->`composio`, `nango_aggregator`->`nango`). The
   single invariant: **registration key == adapter module filename == lookup key**. The engine
   dispatches the ADAPTER on `adapter_key_for(spec)`; `integration_style` selects the validator
   branch (and, for aggregators only, the adapter key). Wave-3 plans register their own modules
   under that key. `aggregate_mcp` has no adapter this phase -> import-miss -> stub (intended).
4. **Real execute(call)** — signature changes from `(name, parameters)` to take the `ToolCall`
   (Pitfall 2: spans/resolver/failed-row all need task/tenant correlation). Flow: resolve
   credential -> validate input (04-02, fail-closed direct-only) -> dispatch via
   `get_adapter(adapter_key_for(spec))` (or stub when no adapter/creds) -> validate output
   (quarantine on violation) -> emit the D-10 tool-event span. Keep the exact existing stub dict
   shape as the no-creds/no-adapter fallback (D-11).
5. **D-10 tool-event span (closes OBS-01)** — `observability.tool_event_span(...)` copying the
   `_approval_span` contextmanager shape (no-op when OTel absent; correlation keys via
   trace_metadata; tool-specific attributes; never raw creds/payloads).

Purpose: A single chokepoint that resolves creds at call time, validates the boundary, emits
the deferred OBS-01 tool span, and lets adapters plug in without touching execute().
Output: gateway.py engine + credentials.py + adapters registry + tool_event_span + default-lane
tests proving cred-only-in-execute, stub degradation, lazy-import dispatch, and span emission.
</objective>
