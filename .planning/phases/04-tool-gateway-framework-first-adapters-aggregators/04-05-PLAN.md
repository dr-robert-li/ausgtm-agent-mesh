## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gateway -> HubSpot API | bearer token + agent params cross to a real SaaS write |
| adapter -> token | the private-app token is resolved by the gateway and passed in; must not be logged/leaked |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-05-01 | Tampering | a live create_deal mutating production HubSpot | mitigate | D-07: live writes hit a HubSpot dev/test SANDBOX only; resource_bindings.pipeline_id points at the sandbox pipeline; documented in docs/credentials/hubspot.md |
| T-04-05-02 | EoP | create_deal executing without approval | mitigate | hubspot_create_deal is category=write -> approval_required (manifest invariant); the adapter is reached only after runner._resume_after_approval is_approved() (unchanged SEC-01/02); the adapter itself performs no gating bypass |
| T-04-05-03 | Information disclosure | the bearer token leaking into logs/results | mitigate | token resolved only inside execute() (04-03), passed to the adapter as `credential`, never returned in the result dict nor logged |
| T-04-05-SC | Tampering | hubspot-api-client install (supply chain) | mitigate | blocking-human package-legitimacy checkpoint (this plan, gate=blocking-human) before any install; [ASSUMED] until verified against pypi.org/developers.hubspot.com |

No high-severity threat left open: production writes are sandbox-isolated, the write stays approval-gated, and the token never leaks.
