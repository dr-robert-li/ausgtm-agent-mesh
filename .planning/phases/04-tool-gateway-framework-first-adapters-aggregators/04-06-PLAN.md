<objective>
Ship the first half of the full Google Workspace direct suite (D-08): the shared OAuth/refresh
auth scaffold plus the Drive (read), Gmail (send, approval-gated), and Sheets (append,
approval-gated) operations, as an own-file module registered with the 04-03 registry. One
OAuth client + a stored refresh token drives a single `google-api-python-client`; reads run
unconditionally in the live lane, writes/sends are approval-gated through the existing ledger.
The adapter degrades to the gateway stub when `GOOGLE_WORKSPACE_OAUTH` is absent (D-11).

Critical (04-03 dispatch contract): all three GWS tools share `provider: google_workspace`, and
execute() dispatches direct tools by `spec.provider`, so this adapter registers EXACTLY ONE
dispatcher under the key `google_workspace` that routes internally by `spec.name`. Registering
once per op would last-wins-collide and silently make Drive/Gmail unreachable (SC-1 defect).

This plan establishes the SHARED auth scaffold (`Credentials(refresh_token=...)` + `build(...)`
per product) AND the single dispatcher's internal op map that 04-07 (Calendar/Docs/Slides)
extends in the SAME file — which is why 04-07 depends on this plan (serialized on the shared
file). Plus the GWS credential/scope doc (D-12 GWS slice), extended by 04-07.

Purpose: prove the direct_api style across the highest-traffic GWS products with one auth path.
Output: GWS adapter (one google_workspace dispatcher routing Drive/Gmail/Sheets), opt-in live
tests (skip without creds), a default-lane adapter unit test, and the GWS credential doc.
</objective>
