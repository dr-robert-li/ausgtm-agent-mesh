<objective>
Prove BOTH aggregator integration styles end-to-end (TOOL-04, D-09): Composio (primary,
MCP-native managed-auth Tool Router — Spike 001 winner) and Nango (fallback, self-hosted OSS
unified API), each making one real READ through the gateway. A read avoids approval-gate
coupling and proves the integration style. Plus the runtime aggregate-schema fetch+cache that
the 04-02 validator's aggregate branch consumes (D-04: aggregate tools validate against the
provider-supplied schema; a missing one NEVER blocks).

Critical (04-03 dispatch contract — the SC-3 half of the flagged blocker): execute() routes
aggregator tools by `adapter_key_for(spec)`, which maps `composio_aggregator`->`"composio"` and
`nango_aggregator`->`"nango"` (NOT the SaaS provider, which for Xero would be `"xero"` and miss).
So these adapters MUST register under those exact aggregator-name keys (matching their module
filenames `composio.py` / `nango.py`) — otherwise a registered adapter with creds present still
falls through to the stub and SC-3 is silently undelivered.

Critical (RESEARCH Pitfall 1): Nango has NO official Python SDK — the PyPI `nango`
package is DO-NOT-INSTALL. Nango integrates via its REST `/proxy` endpoint over the core
`httpx` dep. Composio uses the `composio` SDK (`from composio import Composio`).

This plan owns its own adapter files + `aggregate_schema.py` + two credential docs, and adds a
small manifest seam: at least one Composio-style and one Nango-style READ tool entry (the
manifest already has Xero as `nango_aggregator` for Phase 5; this plan adds the minimal
aggregate read tools needed to exercise each style). Manifest edits here do not collide with
04-01 if 04-08 runs after 04-01 (it depends on it).

Purpose: close TOOL-04 — both aggregator styles working, with the runtime-schema mechanic.
Output: Composio + Nango adapters (registered under keys `composio`/`nango`), the schema cache,
opt-in live tests (each skippable on its own creds), a default-lane cache test, and both
credential docs.
</objective>
