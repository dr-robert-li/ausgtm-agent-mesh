Ship the Beehiiv direct adapter (TOOL-03) — `beehiiv_create_post` (publishing write,
approval-gated upstream, always `status:"draft"`). The adapter calls Beehiiv API v2 over core
httpx (no SDK, no new dependency) and degrades to the gateway stub when `BEEHIIV_API_KEY` is
absent (D-11). Beehiiv stays create-only this phase (05-01 froze: no beehiiv read op).

a flat `{id}` — so the output mapping + the 05-01 output schema both nest under `data` or a real
call output_quarantines. (2) create-post is beta / Enterprise-tier-gated; a non-Enterprise key
may 403 — document this; the default lane stubs regardless, the live lane just skips/fails on a
lower tier.

This plan touches ONLY `tools/adapters/beehiiv.py` + its two tests + its doc. It does NOT edit
the manifest, schemas, pyproject, the registry, gateway.py, or the README / credential-docs
guard (05-01 / 05-07) — so it runs parallel with the other four wave-2 adapter plans.

Op-name contract (05-01): register EXACTLY ONE dispatcher under `beehiiv` routing by `spec.name`
via `_BEEHIIV_OPS = {"beehiiv_create_post": _create_post}`. The key MUST match the manifest op
name 05-01 froze.

Purpose: prove the direct_api style on a publishing provider whose real response nests under
`data` (the canonical quarantine-avoidance case).

draft + nested-output assertion), opt-in live test, credential doc.
